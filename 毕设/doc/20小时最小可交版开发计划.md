# 20小时最小可交版开发计划

> 适用课题：基于DTU与645规约的电表数据采集物联网网关的设计与实现  
> 当前目标：**20小时内做出“能演示、能讲清楚、能继续升级”的基础版本**  
> 技术路线：**C++核心 + Python FastAPI接口层 + Vue展示层**

---

## 一、先明确：20小时要做到什么程度

### 1.1 20小时目标不是“做完毕设”
20小时只做：
- 一个**最小完整链路**
- 一个**能向老师演示的基础版本**
- 一个**后面能继续升级成毕业设计正式版/论文版**的骨架

### 1.2 20小时后必须达到的效果

完成后，你至少应当能演示：

```text
模拟电表数据/645报文
   ↓
C++程序解析645数据
   ↓
转成结构化JSON
   ↓
发布到MQTT或写入本地缓存
   ↓
Python FastAPI提供查询接口
   ↓
前端或接口页面看到数据
```

### 1.3 20小时后暂时不强求的内容
以下内容先不追求完整：
- 真正复杂的多电表轮询
- 很完善的串口联调
- 很复杂的任务调度系统
- 很完整的云平台规则引擎
- 论文级实验图表
- 自适应算法

## 二、题目要求拆分：哪些现在必须做，哪些后续补

## 2.1 当前阶段必须完成（最小可交版）

### A. 技术方案设计
必须有：
- 系统架构图
- 模块划分
- 数据流说明

### B. 645规约数据编码/采集/解析
必须有：
- 645报文基本结构解析
- 常见数据项解析（如电压、电流、有功电能等）
- 校验和验证

### C. 监测任务编制与配置
必须有一个最小版本：
- 电表地址
- 采集周期
- 采集项列表
- MQTT主题
- HTTP查询路径

建议用一个 `config.json` 先做，不做复杂界面。

### D. MQTT接口
必须有：
- 解析后的数据能发布成MQTT消息
- 主题命名清晰

### E. HTTP接口
必须有：
- 查询“最新一次采集数据”的接口
- 查询“当前配置”的接口

### F. 数据展示
必须有其一：
- 简单Vue页面
- 或 FastAPI Swagger + JSON接口演示

### G. 数据上传/存储闭环
必须有其一：
- 发到本地MQTT Broker + 本地SQLite存储
- 或 发到云平台的最小验证版

## 2.2 当前阶段可以先简化处理的内容

### A. 现场设备选型
先写说明，不一定立刻买齐真设备：
- DTU：先用Linux主机模拟
- 电表：先用模拟645报文
- Broker：先用本地mosquitto
- 云平台：后面接ONENET/阿里云

### B. 串口通信
如果真实串口没法马上打通：
- 第一阶段先用文件输入/模拟报文驱动解析
- 第二阶段再接串口

### C. 公共物联网平台
当前只要预留接口，不强行第一版全部打通。

## 三、推荐的最小系统架构

```text
[模拟645报文 / 串口输入]
          ↓
[C++ dtu_core]
- 645帧解析
- 数据项解析
- 配置加载
- 本地缓存(SQLite/JSON)
- MQTT发布
          ↓
[Python FastAPI]
- 查询最新采集结果
- 查询当前监测配置
- 提供给前端调用
          ↓
[Vue页面 / Swagger演示]
- 展示电表数据
- 展示时间戳
- 展示在线状态/采集状态
```

## 四、20小时任务切分

## 第1阶段（0-4h）：把骨架搭起来

### 目标
把项目结构搭好，后面不乱。

### 任务
1. 建立目录结构
2. 确定模块边界
3. 准备一份模拟645报文
4. 写配置文件

### 建议目录

```text
毕设/
├── dtu-core/
│   ├── include/
│   ├── src/
│   ├── tests/
│   └── config/
├── api-server/
│   ├── app/
│   └── requirements.txt
├── meter-monitor/
└── doc/
```

### 配置文件最低要求

```json
{
  "meter_id": "000000000001",
  "poll_interval_sec": 10,
  "data_items": ["voltage", "current", "active_energy"],
  "mqtt_topic": "dtu/meter/000000000001",
  "http_port": 8000
}
```

### 本阶段产出
- 项目目录可用
- 配置文件可读
- 模拟报文准备完成

---

## 第2阶段（4-8h）：完成645解析最小闭环

### 目标
输入一帧645报文，能解析出结构化数据。

### 任务
1. 实现645帧结构解析
2. 实现校验和验证
3. 实现BCD转换
4. 解析2-3个关键数据项

### 当前最低支持数据项
建议先只做：
- 电压
- 电流
- 有功总电能

### 本阶段产出
输入示例报文后，输出类似：

```json
{
  "meter_id": "000000000001",
  "timestamp": "2026-03-08 10:00:00",
  "voltage": 220.4,
  "current": 5.12,
  "active_energy": 1024.55
}
```

---

## 第3阶段（8-12h）：把数据发出去

### 目标
解析后的数据能够被外部看到。

### 任务
1. 接入MQTT客户端
2. 发布解析结果到指定主题
3. 本地落一份最新数据（JSON文件或SQLite）
4. 记录简单日志

### 为什么这里要加本地落盘
因为后面：
- FastAPI好读
- 前端好展示
- 论文实验好统计

### 本阶段产出
- MQTT能收到消息
- 本地能查到最新数据

## 八、后续升级路线（简单版）

## 8.1 本科毕设 -> EI 的升级路线

### 你需要额外补的内容
1. 可靠性实验
   - 丢包率 10% / 20% / 30%
   - 延迟 50ms / 100ms / 200ms
   - 断网恢复实验

2. 对比策略
   - 无缓存无重传
   - 固定重传
   - 缓存+重传

3. 结果图表
   - 数据完整率
   - 平均恢复时间
   - 重传次数

### 适合的情况
- 工程做得完整
- 方法创新一般
- 希望先稳一点发出去

---

## 8.2 本科毕设 -> SCI三区 的升级路线

### 你需要再额外补的内容
1. 一个轻量可命名的方法
   - 例如自适应重传策略
   - 或网络状态感知发送策略

2. 更系统的对比实验
   - baseline更完整
   - 指标更多

3. 更强的分析
   - 为什么有效
   - 在不同网络条件下表现差异

### 适合的情况
- 系统完整
- 实验数据好
- 能加一点策略创新
- 有机构/导师协助改写投稿
